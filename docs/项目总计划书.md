## 文档使用说明（开始实施前先看）

本计划是**项目总纲 + 验收依据 + 学习记录入口**，而不是让你一口气完成的代码生成清单。

- **学习目标优先于功能数量**：重要的是亲自实现、解释、排错和验证，而非堆出大量 Controller 或依赖。
- **保持阶段 0～7 顺序和边界**：0 需求/设计 → 1 MVC/单表 → 2 关联与开课 → 3 选退课并发 → 4 成绩/复杂 SQL → 5 权限 → 6 质量 → 7 交付。不以“尚未加入 Redis/AI”判定第一版不完整。
- **任务粒度**：每次从当前阶段拿出一个最小可验证任务；学习时按“讲解 → 示例 → 小任务 → 自己操作 → 检查纠错 → 下一步”进行。不要预先生成全部业务代码。
- **P0 必做 / P1 加固 / P2 以后再做**：阶段 0～7 的核心验收属于 P0；额外调优与体验改进可作为 P1；Redis、MQ、Kubernetes、RAG 等属于 P2，首版不实施。
- **进度真实性**：本文中未完成的任务保持 `[ ]`；只有实际代码、验证记录与提交证据齐全，才改为 `[x]`。本次只是修订文档，没有开始编码。

### 首版不得破坏的五个数据不变量

1. 对每个开课班级：`0 <= enrolled_count <= capacity`。
2. 对每个开课班级：`enrolled_count == SELECT COUNT(*) FROM enrollment WHERE section_id = ?`（首版退课采用物理删除）。
3. 对每位学生、每学期、每门课程：有效选课的开课班级数最多为 1；同时不存在上课时段冲突。
4. 只有 `grade_publish_status = PUBLISHED` 的班级，学生才可以通过自己的查询接口获得分数；未录齐不得发布。
5. 所有修改都受授权和状态条件控制，不能通过并发或重复请求绕过业务规则。

## 一、项目目标和亮点

### 1.1 项目目标

开发一个支持**学生、教师、管理员**使用的选课与成绩管理后端。系统不仅提供 CRUD，还要处理学期、开课班级、选课时间窗口、容量限制、时间冲突、退课、成绩录入与发布等实际业务，并保证并发情况下的数据正确性。

最终交付应达到：

- 能用 API 完整演示从“创建课程 → 发布开课计划 → 学生选课 → 教师录入成绩 → 成绩发布 → 学生查询”的业务闭环。

- 能独立解释表设计、事务边界、关键 SQL、冲突处理和权限设计。

- 有可重复执行的自动化测试、并发测试、部署配置及接口文档。

- 有可展示的 Git 历史、架构图、核心流程图、测试结果与 README。

### 1.2 项目核心亮点（必须真正实现，不只写在 README）

| 亮点 | 要解决的业务问题 | 技术实现 | 展示证据 |
|---|---|---|---|
| **高并发防超选** | 最后一个名额被多人抢占 | 条件 UPDATE + InnoDB 行锁 + 事务 + 唯一约束 | 并发请求测试、容量不超限断言 |
| **选课规则与冲突检测** | 同一学生选入冲突课程，或同学期重复选同一门课的不同班级 | 学期/课程建模、课表查询、锁定学生记录并做并发安全校验 | 时间冲突、同课程跨班重复、并发边界用例 |
| **整班成绩发布工作流** | 单个学生未录入成绩时不允许部分公开 | `course_section` 统一发布状态、发布前完整性检查、教师归属校验 | 未录齐阻止发布、整班发布、发布后禁止修改的测试 |
| **权限与数据隔离** | 学生不能替别人选课，教师不能修改非本人开课班级成绩 | Spring Security + 登录鉴权 + 角色和资源归属校验 | 401/403/越权测试 |
| **可靠性与工程交付** | 重复请求、异常回滚、部署难复现 | 唯一约束、幂等策略、集成测试、Docker Compose | 回滚测试、重复请求测试、一键启动说明 |

**原则**：以并发选课和业务规则为技术主亮点；安全、自动化测试和部署构成工程亮点。第一版拒绝为了技术名词堆叠而引入微服务、MQ 或 Kubernetes；未来扩展不计入首版验收。

## 三、业务范围及边界

### 3.1 必须完成的业务

1. **学生管理**：学号唯一、增改查、状态管理、条件分页。

2. **教师管理**：工号唯一、基本信息、负责的开课班级查询。

3. **课程管理**：课程编号、学分、基础容量规则及课程信息管理。

4. **学期与开课管理**：课程按学期创建开课班级（Section），明确授课教师、容量、上课时段、选课时间窗口。

5. **选课/退课**：校验学生和开课状态、名额、同一学期同一课程只能选一个班、时间冲突；退课遵守截止时间和成绩规则。

6. **成绩管理**：教师为本人开课班级逐人录入/修正成绩；所有有效选课学生成绩录齐后，按班级一次性发布；发布前不对学生可见，发布后第一版不支持修改。

7. **查询与统计**：我的课表、课程名单、课程成绩分布、学生学期平均分/排名，含分页和复杂 SQL。

8. **认证与权限**：学生、教师、管理员基础登录；学生仅操作本人，教师仅操作所授课班级，管理员管理基础数据。

### 3.1.1 角色与典型用例

| 角色 | 允许的典型行为 | 不应允许的行为 |
|---|---|---|
| 学生 | 查询本人的选课和课表；在窗口内为自己选/退课；查询已发布的本人成绩 | 替其他学生选课；查看未发布成绩；修改教师录入的分数 |
| 教师 | 查询本人负责的开课班、班级名单；录入/修正草稿成绩；满足条件后统一发布 | 修改非本人班级成绩；获取不相关学生的敏感信息 |
| 管理员 | 管理学生、教师、课程、学期、开课班级；调整合规容量；变更允许的状态 | 绕过人数下限调整容量；在 `OPEN` 后随意改课表；直接跳过成绩录齐校验 |

**业务名词**：`course` 是课程目录（如“数据库原理”）；`course_section` 是某学期某课程的实际开课班（如“2027 春数据库原理 01 班”）；`section_schedule` 是该班每周的上课时段；`enrollment` 是学生对开课班的有效选课记录。它们不应互相替代。

### 3.1.2 一条可演示的主业务链

1. 管理员建学期、课程、教师和学生。
2. 管理员为课程创建一个或多个开课班级、排入上课时段、设置容量与选课窗口；完成检查后将班级从 `DRAFT` 变为 `OPEN`。
3. 学生在窗口内查询课程，发起选课；Service 同时验证身份、课程重复、课表冲突、名额和状态，并写入选课记录。
4. 另一名学生竞争最后一个名额；数据库保证最多一人占到该名额。
5. 选课窗口结束后，教师为自己开课班级全部学生录入成绩；未全部录入时发布被拒绝。
6. 教师整班发布；学生只能查看自己所在已发布班级的成绩，管理员/教师根据各自权限查询统计。
7. 使用 README、测试命令、SQL 查询与 Docker 环境重演上述流程。

### 3.2 本次已确认的业务规则（第一版必须落实）

**规则 A｜同学期同课程只能选一个班级**

- 判定维度为 `(student_id, semester_id, course_id)`，不是仅 `(student_id, section_id)`。学生已选择某课程 A 班时，同学期不能再选择其 B 班；不同学期是否重修按第一版规则允许。
- 不新增冗余字段或额外表来硬凑三列唯一约束：第一版统一在选课事务中**先锁定学生行，再查询该学生同学期选课**并拒绝重复。`UNIQUE(student_id, section_id)` 继续防止同班重复，不能误称其能防跨班重复。
- 所有创建有效选课记录的入口必须复用同一事务和锁协议；并发测试必须覆盖“同时请求同一课程的两个不同班级”。

**规则 B｜开课信息修改限制**

- 开课班级状态为 `DRAFT` 时可调整上课时间及容量；**转为 `OPEN` 后冻结 `section_schedule`**，不提供直接更改上课时间的常规接口。第一版不做复杂调课与冲突重排。
- `OPEN` 后仍可调整容量，但必须满足 `new_capacity > 0` 且 `new_capacity >= enrolled_count`；更新必须用带条件的 SQL，在数据库行级竞争下判断，不允许先查询人数、脱离事务后直接覆盖容量。
- 第一版不允许将已发布成绩的班级重新开放选课，也不允许通过修改截止时间绕过这一规则。扩展调课、审批等留到后续版本。

**规则 C｜整班成绩统一发布**

- 每个 `course_section` 统一维护成绩发布状态 `DRAFT → PUBLISHED`；`enrollment.score` 仅保存该学生分数，不再给每条选课记录单独维护发布状态。
- 为避免人数变化影响发布结果，**只能在选课/退课窗口已结束后发布**；发布前要求该班至少有 1 条有效选课，且**全部有效选课的 `score` 均非 `NULL`**（0 分是有效成绩）。
- 只有授课教师有权录入和发布本人班级的成绩；发布前可以修正，发布后锁定成绩，学生仅能看到 `PUBLISHED` 班级的成绩；第一版不做撤回发布/成绩申诉流程。
- 发布与成绩录入的并发必须串行化：两种写操作都先锁定该 `course_section`，再检查发布状态并读/改 `enrollment`，避免发布前后竞争造成状态与分数不一致。

**规则 D｜长期发展定位**

- 第一版以里程碑 A、B 为硬边界，阶段 0～7 保持不变。首版完成后，可以选做 Redis、工程化/云原生、AI 应用等扩展；扩展项必须有实际需求、可验证结果，不因计划列出就开始实施。

### 3.2.1 第一版业务规则的详细边界（设计默认值）

> 以下是为了让任务可执行而作的**实现默认约定**；与前述四项用户决策不冲突。若实施时发现业务需求变化，应修改约定、测试和文档，不是偷偷改接口行为。

| 事项 | 第一版规则 | 要验证的反例 |
|---|---|---|
| 重复选课 | 同一个 `section` 不重复；同一学期同一个 `course` 不可跨班重复 | A 班已选，再请求同课 B 班返回业务冲突 |
| 不同学期重修 | 可以在不同学期选择同一 `course` 的开课班级 | 去年选过课程，不影响今年选课 |
| 时间冲突 | 同学期同星期且上课区间重叠为冲突；第一版不考虑单双周 | 1～3 节和 3～5 节按半开区间定义，边界无重叠 |
| 选课窗口 | `[enrollment_start, enrollment_end)`，开始时刻允许，结束时刻不允许 | 结束时刻整点请求拒绝 |
| 退课 | 同一选课窗口内、未录成绩、未发布成绩时允许 | 已过截止、已录成绩、重复退课均不可改变人数 |
| 开课课表 | `DRAFT` 可编辑；进入 `OPEN` 后冻结；`CLOSED` 不再开放 | 有学生后尝试更改周几/节次被拒绝 |
| 容量 | 必须大于 0；合法扩容/缩容可进行；不得小于当前人数 | 扩容后可继续选；缩至比实际人数少时拒绝 |
| 成绩 | 0～100，0 是合法成绩；`NULL` 代表未录入 | 某一名学生成绩为 `NULL` 则不能发布；0 分不会被误判 |
| 发布 | 选退课窗口结束、班级至少一人、所有有效选课成绩非空，一次性 `PUBLISHED` | 半班录入不可先公开；重复发布按业务冲突处理 |
| 发布后 | 第一版禁止成绩修改、撤回发布和重新开放选课 | 请求更改分数或重新开放被拒绝 |
| 删除 | 不直接物理删除有历史引用的课程、学生、教师；优先使用停用状态 | 已关联数据不能被破坏性删除 |

**时间片段统一采用半开区间 `[start_slot, end_slot)`**：例如 `[1,3)` 包含第 1、2 节，不含第 3 节。两个区间冲突当且仅当 `a.start < b.end AND b.start < a.end`；同学期且同星期时才比较。阶段 0 先把这个规则写入测试，再实现 SQL。复杂周次、节假日和单双周留到扩展版。

**状态变化示意**：开课状态 `DRAFT → OPEN → CLOSED` 为单向流转；成绩状态独立于开课状态，为 `DRAFT → PUBLISHED`。`OPEN` 只表示班级允许按照时间窗口接受选课，**不代表当前这一刻一定还能选**。时间窗口已结束时，即使状态仍为 `OPEN` 也不接受选退课；由管理员按规则关闭是状态管理的一部分。

## 四、数据库设计（先设计，后编码）

### 4.1 核心表（推荐 8 张）

| 表 | 核心字段（示例） | 关键作用 |
|---|---|---|
| `student` | `id, student_no, name, status` | 学生身份与状态 |
| `teacher` | `id, teacher_no, name, status` | 教师身份 |
| `course` | `id, course_code, name, credit` | 课程目录（不代表某学期的开课） |
| `semester` | `id, code, name, start_date, end_date, status` | 学期 |
| `course_section` | `id, course_id, semester_id, teacher_id, capacity, enrolled_count, status, enrollment_start, enrollment_end, grade_publish_status, grade_published_at, version` | 某门课程的学期开课班级，并承担**整班成绩发布状态** |
| `section_schedule` | `id, section_id, day_of_week, start_slot, end_slot` | 开课班级的上课时间片段 |
| `enrollment` | `id, student_id, section_id, score, created_at` | 当前有效的选课关系与学生分数；**无逐人发布状态** |
| `app_user` | `id, username, password_hash, role, student_id, teacher_id, status` | 身份验证及角色映射 |

> `app_user` 属于后期安全阶段；早期可以用测试身份模拟调用，不应为完成登录而延迟核心业务。时间冲突检测以“同一学期的节次区间”作为第一版模型；若采用真实时钟，需明确时区与日期/周次规则。

**状态约定**：`course_section.status` 管理开课生命周期（例如 `DRAFT`、`OPEN`、`CLOSED`），`course_section.grade_publish_status` 独立管理成绩发布（`DRAFT`、`PUBLISHED`）。两种状态不能混用；发布时写入 `grade_published_at`，默认 `NULL`。为简化第一版，选课与退课统一以 `enrollment_end` 为截止时间，且要求在成绩发布前已结束；不额外设计独立退课时限字段。

### 4.1.1 八张表的字段设计草案（阶段 0 再确定最终 DDL）

| 表 | 建议的关键字段与类型 | 约束和设计理由 |
|---|---|---|
| `student` | `id BIGINT`, `student_no VARCHAR(32)`, `name VARCHAR(64)`, `status VARCHAR(16)`, `created_at`, `updated_at` | 学号唯一；状态启用/停用，停用不应直接删选课历史 |
| `teacher` | `id BIGINT`, `teacher_no VARCHAR(32)`, `name VARCHAR(64)`, `status VARCHAR(16)` | 工号唯一，授课班级通过外键关联 |
| `course` | `id BIGINT`, `course_code VARCHAR(32)`, `name VARCHAR(128)`, `credit DECIMAL(4,1)`, `status` | 同一门课程跨学期复用，不把开课容量放在课程目录里 |
| `semester` | `id BIGINT`, `code VARCHAR(32)`, `name`, `start_date DATE`, `end_date DATE`, `status` | 学期代码唯一，起止日期合法且不互相矛盾 |
| `course_section` | `id`, `section_code`, `course_id`, `semester_id`, `teacher_id`, `capacity INT`, `enrolled_count INT`, `status`, `enrollment_start`, `enrollment_end`, `grade_publish_status`, `grade_published_at`, `version` | 与具体开课班级有关的可变属性都放这里；建议 `(semester_id, section_code)` 唯一 |
| `section_schedule` | `id`, `section_id`, `day_of_week TINYINT`, `start_slot SMALLINT`, `end_slot SMALLINT` | 星期 1～7，`start_slot < end_slot`；一班可有多个不重叠时段 |
| `enrollment` | `id`, `student_id`, `section_id`, `score DECIMAL(5,2) NULL`, `created_at`, `updated_at` | `UNIQUE(student_id, section_id)`，0 分合法；物理删除表示退课；不保存逐人发布状态 |
| `app_user` | `id`, `username`, `password_hash`, `role`, `student_id NULL`, `teacher_id NULL`, `status` | 一个账号映射一类主体；角色与主体关系须校验，首版不做多角色叠加 |

补充说明：

- `BIGINT` 主键可自增；是否统一使用 `UNSIGNED` 与 Java 类型对应，阶段 0 一次确定。金额/成绩/学分使用 `DECIMAL` 比 `FLOAT` 更符合固定精度需求。
- 适当添加 `NOT NULL`、`CHECK`、外键和创建/更新时间；但**外键是否统一启用**必须是全项目一致的决策，不能一半靠数据库、一半靠隐式约定。
- `enrollment` 不冗余存储 `semester_id`/`course_id` 时，无法直接靠普通唯一索引实现三元业务唯一性；暂靠统一锁协议与服务层校验。未来若出现其他系统直接写库，优先重新评估持久化约束模型，而不是自信地说“绝对不会重复”。
- 如设计成绩加权统计，第一版先明确统计公式：**普通平均分**为已发布成绩的算术平均；**学分加权平均**为 `SUM(score * credit)/SUM(credit)`，两者不能混为一谈。可以优先完成普通平均和排名，加权平均作为加固任务。

### 4.1.2 表之间的逻辑关系

```text
course (1) ── (N) course_section (N) ── (1) semester
                         │
                         ├── (N) section_schedule
                         ├── (N) enrollment (N) ── (1) student
                         └── (1) teacher

app_user ──> student 或 teacher（根据 role 选择）
```

建议先画出上述关系，再补主键、外键、唯一键和索引。`section_schedule` 的时间与 `enrollment` 的学生状态、成绩状态不应混在一起；这是后续变更不互相牵扯的基础。

### 4.2 核心约束

- `student.student_no`、`teacher.teacher_no`、`course.course_code`、`semester.code` 唯一。

- `enrollment` 建立 `UNIQUE(student_id, section_id)`，从数据库层面防止同一个开课班级的重复选课。
- **跨班同课程限制**：`(student_id, semester_id, course_id)` 的业务唯一性需要 JOIN `course_section` 判定；由于 `semester_id/course_id` 不在 `enrollment` 中，前述唯一索引无法直接保证。第一版通过锁定学生记录、在事务中重新检查并统一所有写入口实现；其正确性须用并发测试验证。

- **第一版退课采用物理删除 `enrollment`**（只允许 `enrollment_end` 前、成绩尚未发布且无已录入分数的记录退课）；如要保留退课历史，可另建事件/审计表。**不要直接在保留 `UNIQUE(student_id, section_id)` 的情况下添加固定 0/1 逻辑删除来替代物理删除。**

- `course_section.capacity > 0`，`0 <= enrolled_count <= capacity`；必要时增加数据库 CHECK，服务层仍需校验。容量调整要求 `new_capacity >= enrolled_count`，使用单条条件 UPDATE 做原子校验。
- `section_schedule` 在开课状态变为 `OPEN` 后冻结；应用层须拒绝对已开放班级的时间修改，避免已选学生课表因后续调整而冲突。

- `enrollment.score` 为 `NULL` 表示未录入，非空时为 0～100（包括 0 分）；`course_section.grade_publish_status=PUBLISHED` 才允许学生看到成绩。发布前先确认有效选课人数非零且所有成绩已录入，发布后禁止修改。

- `course_section` 必须属于有效学期、教师和课程；选课关系使用外键或明确的应用层参照完整性策略。

- 课程满员、学期状态、选课时间、时间冲突等属于业务规则，数据库约束无法全部替代。

### 4.3 数据一致性设计

**选课**的以下步骤必须在同一个 Spring 事务中执行：

1. 尽早执行 `SELECT ... FOR UPDATE` 锁定**学生行**，使该学生的所有选课/退课操作串行化；读取关键选课状态时必须考虑 MySQL 事务隔离级别和一致性读快照，使用能够看到最新提交状态的查询策略（如当前读），避免先建立旧快照再检查。
2. 校验学生状态、学期状态、开课班级状态、选课时间窗口；同学期查询该学生已选课程及课表，拒绝**同一课程的其他班级**和上课时间冲突的班级。
3. 执行条件 UPDATE 原子占用名额（时间窗口也在事务内再次校验）：

   ```sql
   UPDATE course_section
   SET enrolled_count = enrolled_count + 1
   WHERE id = :sectionId
     AND status = 'OPEN'
     AND grade_publish_status = 'DRAFT'
     AND enrollment_start <= CURRENT_TIMESTAMP
     AND enrollment_end > CURRENT_TIMESTAMP
     AND enrolled_count < capacity;
   ```

4. 必须确认影响行数为 1，再插入 `enrollment`；`UNIQUE(student_id, section_id)` 挡住同班重复请求。若插入失败，之前的容量更新必须回滚。
5. 选课事务全部失败则整体回滚。各路径使用统一锁顺序；不得吞掉异常后继续提交。

**并发边界**：条件 UPDATE 负责防止同班超额，但**单独不能防止同一学生同时选中冲突课程或同一课程的不同班级**。后两者依赖“同一学生先锁学生行→查询当前选课→操作班级”的统一锁协议。必须做真实 MySQL 并发测试；不能把 `UNIQUE(student_id, section_id)` 误写成对跨班重复的数据库兜底。第一版以服务层统一写入口为边界，若将来存在绕过该入口的写入程序，应重新评估是否增加数据库级业务约束模型。

**退课**同样使用一个事务：先锁定学生行，再校验当前有效选课记录、时间窗口和成绩状态（`score IS NULL` 且整班尚未发布）；删除记录并要求恰好删除 1 行，再执行 `enrolled_count > 0` 条件扣减。任一步失败则整体回滚；重复退课不得重复扣减人数。

**修改容量**不另开“读取人数→覆盖容量”的竞争窗口，直接执行条件 UPDATE（事务内验证开课状态和管理权限）：

   ```sql
   UPDATE course_section
   SET capacity = :newCapacity
   WHERE id = :sectionId
     AND :newCapacity > 0
     AND :newCapacity >= enrolled_count;
   ```

验证并发选课与缩容竞争时始终满足 `enrolled_count <= capacity`。`DRAFT` 阶段可安排课表；`OPEN` 后不提供修改课表的常规入口。

**成绩录入/修改**：仅授课教师可以操作。仅在选退课窗口结束后录入，修改成绩的事务先锁定 `course_section`，检查 `grade_publish_status='DRAFT'` 和学生确实属于本班，再写入 0～100 的成绩；若已经发布则拒绝。

**成绩整班发布**：授课教师在单一事务中先锁定 `course_section`，校验选退课已结束、成绩状态未发布、本班至少有一条有效 `enrollment`，并确认不存在 `score IS NULL` 的记录；全部满足后将 `grade_publish_status` 置为 `PUBLISHED` 并写入 `grade_published_at`。发布与成绩修改必须遵守相同锁协议，防止并发竞争。**学生成绩查询 JOIN `course_section` 并筛选已发布班级**；未发布时不得通过统计/报表接口泄露成绩。第一版发布后不可撤回或改分。

**范围说明**：数据库约束、条件更新、锁协议和事务都应通过测试证明；不预设死锁永不发生，遇到数据库死锁/超时应回滚并提供合理错误处理，必要时再评估受控重试。

### 4.3.1 事务入口与锁顺序的可执行约定

| 写操作 | 首先锁什么 | 随后做什么 | 不变量 |
|---|---|---|---|
| 学生选课 | 当前学生 `student` 行 | 查询该学生当前学期选课 → 条件占用目标 `course_section` 名额 → 插入 `enrollment` | 不重复、无冲突、不超额 |
| 学生退课 | 当前学生 `student` 行 | 校验原选课 → 删除 `enrollment` → 扣减班级人数 | 不重复扣减、人数一致 |
| 管理员调整容量 | 目标 `course_section` 行（由原子 UPDATE 获取） | 检查状态、`new_capacity >= enrolled_count` | 不小于已选人数 |
| 管理员编辑草稿课表 | 目标 `course_section` 行 | 确认仍为 `DRAFT` → 更新 `section_schedule` | OPEN 后课表不变 |
| 管理员开放班级 | 目标 `course_section` 行 | 校验安排完整 → 状态变为 `OPEN` | 开放与编辑课表互斥 |
| 教师录入成绩 | 目标 `course_section` 行 | 校验窗口结束且 `DRAFT` → 修改本班 `enrollment.score` | 发布后不可改分 |
| 教师整班发布 | 目标 `course_section` 行 | 检查所有分数完整 → 设置 `PUBLISHED` | 不发生部分发布 |

注意：不同操作拥有不同锁路径并不自动代表永远无死锁。应避免在持有班级锁时再反向尝试获取学生锁；若未来改变退课或成绩规则，需要重新审查整个锁图与事务边界。

**隔离级别建议**：阶段 3 可将选退课业务事务显式设为 `READ_COMMITTED`，先锁学生行，再执行新的已选课程/时间冲突查询，确保取得锁后看见其他事务已提交的结果。若选择默认 `REPEATABLE_READ`，必须认真区分快照读和当前读，不能让事务早期旧快照破坏并发校验。**不要只靠一次普通 SELECT 然后盲目插入**。

**事务伪代码（帮助理解，并非可直接运行的实现）**：

```text
@Transactional
选择开课班级(studentId, sectionId):
    锁定 student(studentId)  # SELECT ... FOR UPDATE
    检查学生、学期、班级及选课窗口
    查询学生在本学期的当前选课
    若同一 course 已选 -> 业务冲突
    若与任何已选课表区间重叠 -> 业务冲突
    UPDATE section SET enrolled_count = enrolled_count + 1
      WHERE 状态/时间合法 AND enrolled_count < capacity
    若影响行数 != 1 -> 业务冲突（无名额或不可选）
    INSERT enrollment(studentId, sectionId)
    返回成功；任一步异常抛出，事务回滚
```

**特别区分**：重复相同请求“不造成二次扣名额”属于结果层面幂等；首版可对重复选课返回 `409`，对重复退课返回 `404/409`（整个 API 选定一种一致约定）。这并不等于已支持 `Idempotency-Key` 这种请求级幂等机制，简历不要混写。

### 4.3.2 关键 SQL 思路（供阶段 3、4 验证）

**同学期同课程重复选择的查询方向**：

```sql
SELECT 1
FROM enrollment e
JOIN course_section cs ON cs.id = e.section_id
WHERE e.student_id = :studentId
  AND cs.semester_id = :semesterId
  AND cs.course_id = :courseId
LIMIT 1;
```

此 SQL 要在锁定学生行且具备正确隔离视图的事务中执行。若只在事务外查询，两个并发请求都可能查到“没有选过”。

**时间冲突检测方向**：查询该学生同一学期已选班级对应的 `section_schedule`，与目标班级的全部时段进行比较；同星期且两半开区间满足 `old.start_slot < new.end_slot AND new.start_slot < old.end_slot` 即冲突。先用纯数据样例验证边界，再实现 XML JOIN SQL，防止节次边界的 `<=`/`<` 写反。

**整班发布前完整性检查方向**：先以班级行锁串行化成绩写操作，再查询：

```sql
SELECT COUNT(*) AS total_count,
       SUM(CASE WHEN score IS NULL THEN 1 ELSE 0 END) AS missing_count
FROM enrollment
WHERE section_id = :sectionId;
```

需要满足 `total_count > 0 AND missing_count = 0`；`score=0` 应算已录入。发布应与检查在同一个事务，且所有成绩写入都遵守先锁班级行的协议。

### 4.4 索引与 SQL

- 为 `enrollment(section_id)`、`enrollment(student_id, section_id)`（与唯一索引复用）、`course_section(semester_id, teacher_id)`、同学期同课程查询及课表 JOIN 相关列建立必要索引，避免仅凭猜测建索引。

- 选课列表、学生课表、同学期同课程重复检测、成绩统计至少各有一条自定义 MyBatis XML SQL；学生成绩 SQL 必须限制整班已发布状态。

- 使用 `EXPLAIN` 检查主要 JOIN/过滤条件，并记录优化前后结果；性能结论需基于可复现测试数据。

### 4.5 数据库索引与执行计划验证记录模板

| 查询或写入 | 预期过滤条件 | 候选索引 | 验证重点 |
|---|---|---|---|
| 查学生当前选课 | `student_id` → `section_id` | `UNIQUE(student_id, section_id)` | 是否走索引、JOIN 扫描行数 |
| 查某班名单 | `section_id` | `INDEX(section_id)` | 是否避免全表扫描 |
| 查某学期课程班 | `semester_id`、`course_id` | `INDEX(semester_id, course_id)` | 条件选择性、排序、分页 |
| 查教师所授班级 | `teacher_id`、`semester_id` | 根据实际过滤顺序验证 | 不盲目堆多个近似索引 |
| 查学生课表 | 学生、学期、时间 JOIN | 相关外键索引 | JOIN 顺序和返回行数 |
| 查成绩统计 | `section_id`、成绩发布状态 | 适度复用现有索引 | 聚合成本、测试数据规模 |

每个需要优化的 SQL 记录“SQL 文本 → 样本数据量 → EXPLAIN 结果 → 改动 → 再次测量”；不要只看 `key` 不为空就宣称优化成功，也不要预设数据量极小时一定体现索引收益。

## 五、项目架构与工程规范

### 5.1 基础架构

```text
HTTP/API
  ↓
Controller（请求、校验、响应）
  ↓
Service（业务规则、权限、事务）
  ↓
Mapper（MP CRUD / XML SQL）
  ↓
MySQL
```

目录参考：`controller/`, `service/`, `service/impl/`, `mapper/`, `entity/`, `dto/`, `vo/`, `config/`, `security/`, `exception/`, `common/`。**按实际需要创建包，不提前建空目录。**

### 5.2 工程约定

- Controller 不直接操作 Mapper；业务规则放 Service；跨表事务放在清晰的 Service 入口。

- 请求用 DTO、输出用 VO，不直接把含密码等敏感字段的 Entity 返回给客户端。

- 参数校验与业务校验分开；统一处理校验失败、资源不存在、业务冲突、权限不足、系统异常。

- API 使用恰当的 HTTP 状态码；重点区分 400、401、403、404、409、500。

- 日志要能定位接口请求、业务错误和数据库异常；脱敏，不回显底层堆栈给客户端。

- `@Transactional` 的代理调用、自调用失效、异常吞掉后不回滚等问题必须在项目中验证；选课、退课、成绩修改和发布明确统一事务入口与锁顺序。

### 5.3 API 契约草案（以 REST 为参考，阶段实施时定稿）

> 路径只用于明确边界，不要求立刻生成接口；建议统一 `/api/v1` 前缀。阶段 5 引入真实登录身份后，学生操作优先用 `/me`，不要相信请求体里随意传来的 `studentId`。阶段 0～4 的测试身份只能来自开发/测试环境受控配置，正式运行时不可开放“伪造身份”参数。

| 业务 | 方法与路径（示例） | 角色 | 核心行为或错误 |
|---|---|---|---|
| 新增学生 | `POST /api/v1/students` | 管理员 | 非法参数 400；重复学号 409 |
| 学生列表 | `GET /api/v1/students?page=1&size=10` | 管理员 | 条件分页、限制最大页大小 |
| 新增课程 | `POST /api/v1/courses` | 管理员 | 课程编号唯一、学分合法 |
| 创建开课班级 | `POST /api/v1/sections` | 管理员 | 关联课程/教师/学期；初态 DRAFT |
| 设置课表 | `PUT /api/v1/sections/{id}/schedules` | 管理员 | 仅 DRAFT；内部时间段不重叠 |
| 开放班级 | `POST /api/v1/sections/{id}/open` | 管理员 | 检查排课/时间窗口；冻结课表 |
| 调整容量 | `PATCH /api/v1/sections/{id}/capacity` | 管理员 | 新容量不得小于已选人数，失败 409 |
| 查询开课列表 | `GET /api/v1/sections?semesterId=...` | 登录用户 | 过滤、分页、可选余量 |
| 我的选课 | `GET /api/v1/me/enrollments` | 学生 | 仅本人记录 |
| 选课 | `POST /api/v1/me/enrollments` | 学生 | body 含 `sectionId`；冲突返回 409 |
| 退课 | `DELETE /api/v1/me/enrollments/{id}` | 学生 | 仅本人，截止后/有成绩不可退 |
| 我的课表 | `GET /api/v1/me/schedule?semesterId=...` | 学生 | XML JOIN，正确过滤学期 |
| 教师班级名单 | `GET /api/v1/teacher/sections/{id}/roster` | 所授教师 | 资源归属校验 |
| 录入成绩 | `PUT /api/v1/teacher/sections/{id}/scores/{enrollmentId}` | 所授教师 | 0 分有效、发布后禁止修改 |
| 整班发布 | `POST /api/v1/teacher/sections/{id}/grades/publish` | 所授教师 | 必须全班录齐，事务原子发布 |
| 我的成绩 | `GET /api/v1/me/grades?semesterId=...` | 学生 | 只返回已发布分数 |
| 成绩统计 | `GET /api/v1/teacher/sections/{id}/statistics` | 所授教师 | 聚合 SQL、空班级/并列名次 |

**响应约定**：字段名和结构统一，错误响应包含机器可识别的 `code`、人可读 `message`、必要时 `requestId`，不要把 SQL 栈信息暴露给客户端。示意：

```json
{
  "code": "ENROLLMENT_COURSE_DUPLICATE",
  "message": "本学期已选该课程的其他开课班级",
  "requestId": "example-request-id"
}
```

建议对分页统一响应 `records`、`total`、`page`、`size`；`page` 从 1 开始，`size` 上限由配置约束。**以上是设计草案，不表示这些接口已经实现。**

### 5.4 错误码与 HTTP 状态码设计

| 场景 | 建议 HTTP | 建议业务 code |
|---|---|---|
| DTO 缺字段、负容量、非法时间片段 | 400 | `VALIDATION_ERROR` |
| 未登录、凭据失效 | 401 | `UNAUTHENTICATED` |
| 已登录但无角色权限或资源不属于本人 | 403 | `FORBIDDEN_RESOURCE` |
| 课程、学生、选课记录不存在 | 404 | `RESOURCE_NOT_FOUND` |
| 同课程跨班重复、时间冲突、名额不足 | 409 | `ENROLLMENT_CONFLICT`（可细分） |
| OPEN 后修改课表、缩容低于已选人数 | 409 | `SECTION_STATE_CONFLICT` |
| 成绩未录齐、重复发布、发布后修改 | 409 | `GRADE_STATE_CONFLICT` |
| 未预期数据库错误或程序缺陷 | 500 | `INTERNAL_ERROR` |

数据库唯一约束冲突应映射成适当的业务冲突，不直接把 SQL 异常原文传给前端；发生失败必须核对事务是否已回滚，**错误码不是回滚机制**。

### 阶段 3｜选课与退课（项目核心）

**目标**：掌握跨表事务、数据库约束、容量竞争和时间冲突。

**阶段 3 的实施策略：先保证单线程正确，再验证并发一致性。**

#### 3-A 设计业务状态与不变量

从“谁能选/什么时候能选/哪些课不能一起选/什么叫占到名额”入手，列出选课前置检查的清单。明确每个失败如何返回，例如 `STUDENT_DISABLED`、`SECTION_NOT_OPEN`、`ENROLLMENT_WINDOW_CLOSED`、`COURSE_DUPLICATE`、`SCHEDULE_CONFLICT`、`SECTION_FULL`。

#### 3-B 实现单线程正确性

- 先完成成功选课与退课，验证 `enrollment` 行数、`enrolled_count` 同步变化。
- 逐个加入重复同班、同课程不同班、时间冲突、容量不足、窗口关闭、学生停用等分支。
- 通过 IDEA 断点观察 `@Transactional` 下的 Mapper 调用顺序；验证异常是否回滚已执行的 UPDATE。
- 明确发生主键/唯一键冲突后，不能捕获异常再伪装成业务成功而让已修改的人数提交。

#### 3-C 设计并发安全方案

- **容量竞争**：条件 UPDATE 判断 `enrolled_count < capacity`。最后 1 个名额两个学生同时竞争，最终只能有 1 个成功。
- **同学生竞争**：所有选退课先锁同一个学生行，随后检查同学期课程重复与课表冲突。即使是两个不同的 `course_section`，该学生的请求也需串行处理。
- **容量缩容竞争**：管理员缩容与学生选课都竞争相同 `course_section` 行；最终 `capacity >= enrolled_count`。
- **事务隔离**：以 MySQL 真实测试为准；如使用 `READ_COMMITTED`，确保获得学生锁后才查询当前课程；对 `REPEATABLE_READ` 的快照读区别给出文字说明。

#### 3-D 并发测试操作说明

1. 准备独立 `course_test` 数据库、一个容量为 1 的班级、两个启用学生账号。
2. 用两个线程和 `CountDownLatch` 尽量同时发起选课；线程各自使用独立的数据库事务与连接。
3. 等所有线程结束后，断言成功数 = 1、有效选课数 = 1、`enrolled_count = 1`，失败方有合理错误。
4. 准备同课程的 A、B 两个班，并让**同一学生**两个线程并发选 A/B，断言最终至多一个有效班级。
5. 准备时间冲突的不同课程，重复上述同学生并发实验，断言两门不能一起成功。
6. 在班级已有人选课时，让选课线程与缩容线程竞争，断言最终容量不低于真实人数。
7. 重复执行多轮，记录环境、线程数、种子数据、SQL 日志和最终断言；偶然成功一次不能证明正确性。

**并发测试陷阱**：不要在父测试方法上开启一个覆盖所有子线程的测试事务；各子线程的事务不会自动继承父线程。线程数不能大幅超过连接池可供连接数，不能把连接池耗尽误判为事务逻辑失败。并发测试的目的首先是**正确性**，不是证明“承受海量 QPS”。

**学习成果**：能够分别回答“为什么条件 UPDATE 防超额”“为什么唯一索引只防同班重复”“为什么还要锁学生”“事务失败后修改过的计数为何回滚”“退课重复请求怎样防止计数负数”。

- [ ] 设计并实现选课业务状态和异常分类。

- [ ] 在事务中先锁定学生，完成学生/开课校验、同学期同课程重复检查、课表冲突检查、容量占用和选课记录插入。

- [ ] 使用唯一索引防同班重复选课；通过“锁学生→查该学期已选课程”防同课程不同班重复，不能混淆两者。

- [ ] 同一学生的并发选退课执行统一锁协议，防止同时选中冲突课程或同一课程的不同班级，并验证真实 MySQL 隔离级别下读到最新状态。

- [ ] 退课遵守期限与成绩规则，删除记录和减少人数原子完成。

- [ ] 测试事务回滚、重复选退课、同课程跨班重复、满员竞争、时间重叠、边界时间片段。

- [ ] 并发测试至少覆盖“最后一名额竞争”和“同一学生同时选同课程两个班”；证明 `enrolled_count` 等于有效选课人数。

- [ ] 记录一份《并发选课设计与验证》说明，包含 SQL、事务、锁和测试证据。

**验收（硬门槛）**：任何测试中不得超额选课、不得同班重复或同学期同课程跨班重复、不得重复退课导致人数负数、不得产生冲突课表；缩容并发不得使容量小于已选人数；失败请求对应事务保持一致。

**阶段 3 集中验收点**：暂停扩展新功能，复盘至少两组多线程并发测试、一次事务回滚、一份 SQL/锁顺序说明和关键异常日志；这些证据未通过前，不以“接口能返回成功”作为阶段完成标准。

### 阶段 4｜成绩管理、发布与统计

**目标**：巩固复杂 SQL，形成完整业务闭环。

**阶段 4 的建议实施顺序**：

1. 实现“教师查询本人开课班级名单”，明确 `score = NULL` 是“没有录入”，并不等于成绩 0。
2. 实现逐人录入和修改草稿成绩，校验归属班级、选课窗口截止、分数范围与成绩状态；初期可用测试身份模拟授课教师，阶段 5 再接真实认证。
3. 加入整班发布：对 `course_section` 加锁，检查存在有效选课且全部分数非空，然后在同一事务内写入 `PUBLISHED` 与发布时间。
4. 实现学生“我的成绩”：JOIN 发布状态过滤。教师/管理员根据权限查看相关成绩时，可以查询草稿，但**学生侧任何列表、统计、导出都不能泄露未发布分数**。
5. 实现课程成绩分布、学生学期成绩、平均分和排名；每条复杂 SQL 都要先写出样例数据的人工计算结果，再运行自动化断言。
6. 最后安排“成绩保存 vs 发布”的并发实验：录入操作和发布操作必须先锁同一班级行，不允许已发布后再写入分数。

**统计设计默认值**：

- 第一版考试分数范围为 0～100，使用 `DECIMAL(5,2)` 存储；未录入是 `NULL`，0 分计入统计。
- 平均分默认算术平均，统计范围仅包括学生已发布成绩。若后面需要 GPA 或学分加权平均，应单独定义公式和绩点映射，不能将二者默认等同。
- 排名需说明并列策略：可选 `RANK()`（1,1,3）或 `DENSE_RANK()`（1,1,2），先确定一个并写进测试；不要因为窗口函数能运行就忽略并列语义。
- 没有符合条件的数据，结果为空或相应汇总值为空，应有固定 API 约定；避免除以 0。

**成绩发布的特殊用例**：班级零人、全班已录齐、漏一个 `NULL`、存在 0 分、教师越权发布、重复发布、发布后编辑、发布后学生查询可见性、未发布时学生尝试从统计接口旁路查询。

- [ ] 教师在选退课截止后录入、修正本人班级成绩；校验 0～100，`NULL` 表示仍未录入，0 分属于已录入。

- [ ] 用 `course_section.grade_publish_status` 管理整班 `DRAFT → PUBLISHED`，不要用逐条成绩发布状态；成绩未录齐或班级无人选课时拒绝发布。
- [ ] 发布与成绩修改先锁同一个 `course_section`，整班原子发布、记录发布时间，发布后禁止修改；学生只可查询已发布班级成绩，统计接口不能泄露未发布分数。

- [ ] 生成学生学期成绩单、课程成绩统计、排名。

- [ ] 使用 XML 实现 JOIN、GROUP BY、HAVING、窗口函数、动态条件。

- [ ] 设计必要索引，使用 `EXPLAIN` 分析两条关键 SQL。

- [ ] 完成成绩归属权限、未录齐发布失败、0 分有效、重复发布、发布后非法修改、并发修改与发布、统计正确性、空结果和排名并列测试。

**验收**：能完整演示“选课 → 全班成绩录入 → 整班一次性发布 → 学生查询”；任何未录齐的班级不得发布，发布前学生不可见、发布后不可更改；统计结果和 SQL 经测试验证。

### 阶段 5｜登录鉴权与资源权限

**目标**：使系统从开发测试接口提升为多角色系统。

**阶段 5 的建议实施顺序**：

1. 先建立身份认证：`app_user` 保存用户名、密码哈希、账号状态与对应学生/教师主体。密码使用适当的密码哈希算法（例如 BCrypt）；禁止明文及可逆“加密密码”。
2. 明确认证技术方案，**第一版只选一种**：可用基于 Session 的认证（对传统 Web 更直观）或合适的 Token 方案（对纯 API 测试更方便）。选型理由写进文档；不要为了简历同时实现 Session、JWT、OAuth2。
3. 在 Spring Security 中先实现“未登录返回 401、无权限返回 403、管理员可管理基础数据”的基础规则。
4. **再实现资源归属鉴权**：学生从认证上下文确定自己的 `studentId`；教师对某 `sectionId` 的操作要核对 `teacher_id`，不能仅检查“角色是教师”。
5. 确保 DTO 的 `studentId`、`teacherId` 等不能由客户端随意替换去完成越权操作；审核数据查询是否通过了资源过滤。
6. 重跑阶段 1～4 的正常与异常测试：引入 Security 之后原有业务不能被 401/403、CSRF 或过滤器配置无意破坏。

**权限矩阵（首版）**：

| 操作 | 学生 | 教师 | 管理员 |
|---|---|---|---|
| 管理课程/学期/班级 | 否 | 否 | 是 |
| 查询已开放的课程列表 | 是 | 是 | 是 |
| 选课/退课 | 仅本人 | 否 | 否（不替人绕规则） |
| 查询课表/已发布成绩 | 仅本人 | 本人授课相关数据 | 按管理权限 |
| 录入/修正草稿成绩 | 否 | 仅本人授课班级 | 首版不提供直接绕过教师的改分接口 |
| 整班发布成绩 | 否 | 仅本人授课班级 | 首版不代教师跳过规则 |
| 查询完整管理信息 | 否 | 仅岗位所需 | 是 |

**安全验收**：至少对每个敏感接口测试“未登录 / 错误角色 / 正确角色但操作他人资源 / 正确用户”四种情况。日志里不输出密码哈希、明文密码、Session/Cookie/Token；对 SQL 绑定参数日志也要考虑敏感信息。

- [ ] 使用 Spring Security 建立基本登录认证；密码使用安全单向哈希，不保存明文。

- [ ] 选择并统一会话或 Token 认证方案；明确失效/过期处理。

- [ ] 实现学生、教师、管理员角色权限。

- [ ] 验证学生不能替别人选退课、教师不能录入/发布非本人开课班级成绩，管理员不能绕过开课时间与容量规则。

- [ ] 校验 401/403、非法 Token、越权读写等场景。

- [ ] 不在日志、错误响应中暴露密码或 Token。

**验收**：角色权限正确，越权操作被拒绝；原有业务 API 在真实身份上下文下通过集成测试。

### 阶段 6｜质量、性能与工程化完善

**目标**：将“能用”提升为“稳定、易维护、可测试”。

**阶段 6 的建议实施顺序**：

1. **收敛业务逻辑**：检查 Controller 里是否混入 SQL、Service 是否不必要地互相调用、事务入口是否被自调用绕过代理、权限检查是否散落重复。
2. **回归失败分支**：重点复跑阶段 3 并发与阶段 4 发布相关测试；重构不能破坏已确认的不变量。
3. **性能问题证据化**：选择两个真实的复杂 SQL，建立大小明确的样例数据，记录 `EXPLAIN`、响应耗时、查询行数，再决定是否增加索引或优化 JOIN。
4. **错误与日志**：给同一请求设置可关联的请求标识，确保业务冲突/系统异常能被定位，向客户端输出稳定错误码，而不是数据库栈轨迹。
5. **实际排错训练**：保留至少三条“现象 → 假设 → 观察日志/断点/SQL → 定位原因 → 修改 → 回归测试”的真实案例。不必人为制造线上故障，可用测试环境注入可控失败。
6. **代码审查**：检查命名、空值、事务注解、权限归属、重复 SQL、异常处理、数据泄露、测试隔离；根据 review 真正修改，再提交。

**性能报告不要造数字**。记录机器/数据库版本、连接池配置、数据量、SQL、执行次数与观察结果；若样本太小、噪声大或没有明显变化，应如实描述而不是宣称提高了 XX%。

**建议做一次差错排查演练**：让选课插入阶段发生可控约束冲突；观察 `enrolled_count` 是否回滚。随后验证错误映射是否能把业务冲突转为 409，并且日志足以定位原因。这个练习比再加一组单表 CRUD 更有价值。

- [ ] 检查 Controller/Service/Mapper 职责、DTO/VO 和事务边界。

- [ ] 补齐单元测试与 MySQL 集成测试；使用独立测试数据，运行可重复。

- [ ] 通过可控方式复现事务回滚、唯一约束冲突、同课程跨班并发选课、缩容竞争、整班发布竞争，以及死锁/重试讨论。

- [ ] 检查容量变更/占用、成绩发布等重要 UPDATE 的影响行数，以及必要时的乐观锁失败处理。

- [ ] 分析慢 SQL、索引及 N+1 查询风险；必要时改进分页。

- [ ] 使用 IDEA 断点、调用栈和 MyBatis SQL 日志定位至少 3 个真实问题并记录。

- [ ] 规范异常码、日志、Git 提交历史；完成一次 Code Review 与重构。

**验收**：关键业务测试稳定；并发和事务证据可复现；主要 SQL 及架构决策有说明。

## 七、持续执行的 Git、测试与开发规则

### 7.1 一次开发任务的标准流程

**明确需求 → 明确验收条件 → 先设计 → 独立编码 → 测试 → Code Review → 修复 → Git 提交 → 记录结果。**

- 每次只推进一个有边界的任务；不因建议执行就标记完成。

- 优先独立编写核心代码，AI 用于原理解释、方案比较、代码审查、排障。
- **学习边界**：本人负责需求拆解、关键业务 SQL、事务入口、并发测试和首次调试；AI/Agent 可以辅助重复代码、生成测试思路或检查差异，但必须先读懂并验证代码，不把核心学习任务完全外包。
- 对 AI/Agent 的改动先看 `git diff`，运行相关测试后再提交；失败时先尝试定位调用链、SQL、事务和日志，而不是直接让工具整体重写。

- 简单 CRUD 练一次完整链路即可；后续复用，不做机械重复训练。

- 失败场景必须有测试；涉及数据修改的测试注意清理与隔离。

- 每个模块完成后更新进度、未解决问题与决策记录，不在项目末尾补写所有文档。

### 7.2 Git 必须实际掌握的操作

- [ ] `status / add / commit / log / diff`

- [ ] `.gitignore` 与敏感配置排除

- [ ] `branch / switch / merge`，处理一次实际冲突

- [ ] `fetch / pull / push`，理解 non-fast-forward

- [ ] `restore / revert / stash` 的适用区别

- [ ] 为稳定交付版本创建 Tag

### 7.3 测试级别

- **单元测试**：校验业务条件、错误分支、部分 Service 逻辑。

- **数据库集成测试**：约束、Mapper XML、事务和真实 SQL 行为。

- **API 集成测试**：入参校验、HTTP 状态码、权限与响应结构。

- **并发测试**：竞争最后名额、同一学生并发选冲突课、同课程跨班并发、选课与缩容竞争、重复退课、成绩修改与整班发布竞争。

- **交付烟雾测试**：从干净数据库启动后演示关键 API。

**测试证据不等于只贴一张成功截图**：至少记录场景、输入、期望、实际结果与运行方式。

### 7.4 日常学习和提交规范（控制任务粒度）

- 每次只取 **1 个可验证子任务**，开工前说清“输入是什么、正确输出是什么、失败时如何表现”。
- 新知识：先讲清思想和示例，用户自己完成一段关键代码或 SQL，再检查、纠错和继续；对于重复的样板代码不必增加无意义的手写量。
- 每次结束记录：**已完成、已验证、仍有问题、下一次从哪里继续**；没有执行的任务永远不打勾。
- 发生 bug 时先保留完整证据：请求、日志、SQL、数据库状态、当前分支和修改 diff；先做自己的初步定位，再交给 AI 协助审查。
- Agent 改代码前先明确范围（例如只读审查、只允许改测试、只修某个 Service）；提交前人工查看 `git diff`，测试通过后由自己提交。

**建议提交信息示例**：`feat(student): add validated student creation`、`feat(enrollment): prevent full-section overbooking`、`test(enrollment): verify concurrent selection invariant`、`fix(grade): block publish with missing scores`、`docs: record row-lock strategy`。这些是规范示例，不代表已存在的 Git 提交。

### 7.5 每个模块的“完成定义”（Definition of Done）

只有同时满足以下条件，才把该模块标记完成：

1. 需求及其边界已明确；存在至少一个正常案例、一个失败案例、一个必要边界案例。

## 十、核心交付后的可选技术扩展路线（不计入阶段 0～7）

**执行条件**：只有在里程碑 A、B 完成、主要测试和部署可复现之后才考虑；每次只选一项能解决实际问题的扩展，先定义问题与验收证据再实施。下列方向**不是待办清单，不应直接勾选进度**。

| 方向 | 可用本项目承载的真实问题 | 建议验证方式 | 进入条件 |
|---|---|---|---|
| Redis / 缓存 | 开课列表、课程目录等热点读请求较多 | 对比缓存前后数据库请求数、命中率、失效一致性 | 先有查询指标或明确需求；选课容量仍由 MySQL 事务保证 |
| 持续集成与云原生基础 | 测试、构建、部署重复且容易出错 | CI 自动测试、容器健康检查、结构化日志与可观测性 | Docker Compose 基础交付先稳定，再按需增加迁移/监控工具 |
| 业务进阶 | 课程候补、退课审计、成绩更正申请 | 事件与状态机设计、回归测试 | 明确新业务时再扩表，不在首版提前实现 |
| AI 应用 / Agent | 学生希望用自然语言查询适合的课程 | AI 调用只读课程查询工具，验证授权、参数、结果解释 | 先完成可靠的后端 API 和权限体系，再连接 LLM/Tool Calling |
**AI 扩展示例**：学生提出“推荐 3 学分且不与周三课程冲突的 AI 课程”；AI 可以解析意图、调用只读接口并解释推荐。**任何正式选课都必须由用户明确确认后调用已有业务 API，且权限、时间冲突、名额仍由后端判断**。RAG（课程介绍/培养方案问答）可作为独立后续方向，不强制与首版捆绑。

**扩展原则**：优先在当前单体中增加可独立验证的模块，不为使用新技术而拆微服务或上 Kubernetes。一个扩展最好留下问题描述、设计理由、实现、对照测试、README 更新；扩展失败时不影响稳定的核心系统。

### 10.1 未来扩展的建议优先级

以下不是新的强制阶段，仅供里程碑 A、B 达成后选择：

**路线 1｜Redis + 查询性能**：只针对真实热点查询（课程列表/开课检索）加缓存，建立命中率和数据库访问次数对照。课程容量、是否可选、正式选课写入仍以 MySQL 事务为可信事实来源；讨论缓存过期、主动失效和旧数据可见性。

**路线 2｜工程与云原生**：在稳定 Docker Compose 基础上加入 CI 自动构建/测试、数据库版本迁移、健康指标与日志聚合；先证明问题得到解决，再考虑容器平台编排或复杂发布策略。

**路线 3｜AI 应用**：设计只读的课程查询 Tool API，让 LLM 将自然语言变成带约束的查询参数、调用现有后端并解释结果。必要时增加课程大纲和培养方案的 RAG 问答；**正式选课必须由用户确认，所有权限/学分/冲突/容量规则留在后端执行**。

**路线 4｜业务演进**：需求真实出现时再增加候补队列、操作审计、成绩更正申请。每一项都有新的状态与并发边界，需要新设计和回归测试；不能未经分析就给现有 `enrollment` 随意添加逻辑删除。

建议**一次只选择一个方向、一个真实问题、一套衡量方法**，不把四条路线同时写成下一阶段必须做的任务。
